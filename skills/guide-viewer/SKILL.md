# guide-viewer — 説明が伝わるかを、別の門で見る

**文学の評議会は、説明の明瞭さを測らない。** hook / plot / prose / emotional-power の
10 次元は、物語としての強さを見る。そこでは「断片のほうが強い」「言わないほうが良い」
が高得点になりうる。解説動画には、それとは別の門が要る。

この skill は、**評議会の 11 次元目ではない。** 別の台帳を作り、平均に混ぜない。
文学の点数が高くても、この門を通らなければ採用しない。

## 二つの審査

### 1. 初見復元テスト（3 人）

題材の予備知識のない読者を 3 人、**別々の subagent** として立てる。
渡すのは **台本だけ**。設計・人物票・評議会の結果・採用予定を渡さない。

読者は `facts.yaml` の問い（答えは渡さない）に答える。

- 何が起きたか
- 原因は何か
- どう直したか
- 各数字は、何を測ったものか（分母・単位）
- 意味が取れなかった行（最大 10）
- 理解度（0〜100）

返答は JSON。`schemas/viewer.schema.json` の形に合わせ、`review/viewers/<版>/r1.json`
などに保存する。**読者自身に `recovered`（yes / partial / no）を付けさせる。**
こちらで代筆しない。

### 2. 説明の設計（1 人）

script + `design.md` + `facts.yaml` を読む評価者を 1 人立てる。次を 0〜100 で採点する。

| 次元 | 見るもの |
| --- | --- |
| `fact_coverage` | 事実の柱が、台本の平文で一度は言われているか |
| `causal_chain` | 「なぜ」の鎖が途切れていないか。A が B を招いたことが言われているか |
| `number_hygiene` | 数字に分母・単位があるか。定義されない数字が無いか |
| `term_intro` | 専門語を、使う前に導入しているか |
| `reference_clarity` | 「それ」「その」の受け手が、直前にあるか |
| `information_order` | 問い → 答え → 次の問いになっているか |
| `fact_play_boundary` | 事実と演出の区別が、台本の側でつくか |

返答は `review/viewers/<版>/explanation.json`。`primary_score` と `critical`、
`missing`（欠けた鎖・事実・数字）を残す。

## 手順

1. **`facts.yaml` を書く。** `design.md` の「説明の鎖」から、視聴者が答えられるべき
   事実を 3〜7 個に絞る。id は短い英語（`cause` / `fix` / `numbers` / `timeline`）。
   中身は `research/facts.yaml` の検証済みの事実に合わせる（門の材料だけ別の値にしない）。

   ```yaml
   facts:
     - id: cause
       question: 像がぼやけた原因は何か
       answer: 研磨に使った検査装置のレンズ間隔が1.3mmずれ、鏡が設計と違う形に磨かれた
     - id: fix
       question: どう直したか
       answer: COSTAR が、既知の誤差を光の入り口で打ち消した（鏡は削り直していない）
   ```

2. **読者を 3 人立てる。** `references/viewer-brief.md` の文面に、台本と `facts.yaml` の
   **問いだけ**を差し込む。3 人は互いの返答を見ない。題・作者・版名を渡さない。

3. **説明の評価者を 1 人立てる。** `references/explanation-brief.md` の文面に、
   台本・`design.md`・`facts.yaml` を渡す。

4. **JSON を保存して集計する。**

   ```
   <venv> engine/viewer.py record --project projects/<作品> --version <版>
   <venv> engine/viewer.py table  --project projects/<作品>
   <venv> engine/viewer.py compare --project projects/<作品> --before v6 --after v7
   ```

5. **門を通す。** 既定の条件:

   - 初見の理解度は、**平文の基準の平均 − 10 点以上**（基準を使わないなら 75 以上）
   - すべての事実が、読者の **2/3 以上**に復元されている
   - 説明の評価 **75 以上**、かつ `critical` が無い

   通らなければ、**採用しない。** 台本へ戻る。読者を増やして平均を上げない。

## 理解度のしきい値は、平文の基準から測る

**75 は、平文で書いた解説のための数字。** 人物の掛け合いと感情の層を持つ台本は、
同じ事実でも「意味の取りやすさ」の自己申告が下がる。断片・含み・間を使うためで、
意味を落としたとは限らない。題材そのものが難しい場合、平文でも 75 に届かない。

そこで、同じ事実を平文で書いた**基準版**を用意し、同じ 3 人に読ませる。

1. `review/viewers/<基準>/plain.md` に、`facts.yaml` と `design.md` から平文の台本を書く。
   **掛け合いの台本を読む前に書く。** 台本に合わせて基準を下げない。
2. 読者 3 人に、同じ問いを渡す（`references/viewer-brief.md`）。
3. ```
   <venv> engine/viewer.py baseline --project projects/<作品> --version <基準>
   ```
4. 門は `record --baseline <基準>` で判定する。しきい値は**基準の平均 − 10 点**
   （`--gap`）。

10 点は、掛け合いの調子に許す説明の損失の上限。3 人の平均は ±5 点ほど動くので、
それより小さい差で採否を決めない。**基準が 60 未満なら、平文でも伝わっていない。**
台本ではなく設計（事実の選び方・順序）へ戻る。

**事実の復元（2/3）と説明の評価（75）は、基準を使っても変えない。**
基準が緩めるのは理解度の絶対値だけ。

## 台本へ戻すとき

- **原因の鎖が欠けている** → `design.md` の事実の柱へ戻り、A→B の一文を足す。
  比喩を足さない。
- **数字の分母が無い** → 同じ cue か隣の cue に、分母と単位を置く。
- **専門語が先に出る** → 初出の cue で、一言の定義を置く。
- **「それ」の受け手が無い** → 名詞を繰り返す。文学的な省略をしない。
- **事実と演出の区別が消えている** → `演出で足すもの` を台本の側で分かるようにする。

**感情の層は削らない。** 説明の cue を平文にし、感情の cue は断片のままでよい。
両方を同じ調子にしないことが、この skill の狙い。

## 詳細カードは、門の外側

`video.yaml` の `details`（章の中で切り替わる詳細カード）は、**門の材料にしない。**

- **門が読むのは台本だけ。** カードを読ませて「説明が足りた」ことにしない。
  カードは詳しい事実を置く場所であって、台本の説明の穴を埋める場所ではない。
- **カードの文は、台本で言った事実か `research/facts.yaml` の事実に限る。**
- 台本に無い新しい事実をカードへ足すなら、**先に research へ足し**、必要なら
  `review/viewers/<版>/facts.yaml`（門の材料）にも問いを足して、**門を通し直す**。
  門を通っていない事実を、カードだけに置かない。

## やらないこと

- 文学評議会の平均に、この門の点を混ぜる。
- 詳細カードで、門の欠けた事実を補う。
- 読者に `design.md`・人物票・前の評価を見せる。
- 読者の返答を、こちらで `recovered` に書き換える。
- 平均を上げるために読者を増やす。3 人で足りないなら、台本が悪い。
- 説明を足すために、感情の cue を説明的にする。
